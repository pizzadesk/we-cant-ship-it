WE CANT SHIP IT -- Custom Card Tutorial
=======================================

This walkthrough takes you from a blank copy of the template
to a fully filled-in card ready to submit.


BEFORE YOU START
----------------
Open data/custom_cards/card_template.tres in a plain-text editor.
Save a copy with a new name. Use only lowercase letters, numbers,
and underscores. End the filename with .tres

Good filename:   my_card.tres
Good filename:   telekinesis_system.tres
Bad filename:    My Card.tres          (spaces break the loader)
Bad filename:    template_v2.tres      (no "template" in the name)


STEP 1 -- The header lines
--------------------------
The first six lines of the file tell Godot what kind of file this is.
Do not change or delete them. They look like this:

  [gd_resource type="Resource" script_class="FeatureCard" load_steps=2 format=3]
  [ext_resource type="Script" path="res://scripts/data/feature_card.gd" id="1_xxxxxx"]
  [resource]
  script = ExtResource("1_xxxxxx")

Leave every character exactly as it appears.


STEP 2 -- feature_name
-----------------------
  feature_name = "Your Feature Name"

Replace the placeholder text with the name of your feature.
This is the title shown on the card in-game.

Examples:
  feature_name = "Real-Time Weather Simulation"
  feature_name = "Photo Mode"
  feature_name = "Crafting System"

Rules:
  - Use title case (capitalise the main words)
  - Keep it under about 30 characters or it will overflow the card
  - This is the only required field besides tags


STEP 3 -- description
----------------------
  description = "One sentence. No heroics. Let the feature speak for itself."

Replace the placeholder with a single sentence of flavour text.
This appears on the card and in the tooltip when you hover over it.

Tone guide -- Our cards favour one of these six voices:

  Observer trap       Name the gap between what players expect and what happens.
                      "Players will spend more time in photo mode than the game."

  Spec vs reality     Describe with false confidence what this obviously cannot do.
                      "Fully dynamic. Fully deterministic. Fully untested."

  Player indictment   Address the player like they requested this personally.
                      "You will use this exactly once to see what it does."

  Designer alibi      Frame it as defensible from someone who was not in the room.
                      "Adds perceived systemic depth without introducing systems."

  Contained universe  Give it a scope that sounds like its own game pitch.
                      "Manages fishing rod physics, fish AI, and dock licensing."

  Known issue as feature
                      State the bug as if it were intentional.
                      "Works best when the player does not look directly at it."

Leave description as an empty string if you do not want flavour text:
  description = ""


STEP 4 -- ambition_value and instability_value
-----------------------------------------------
  ambition_value = 5
  instability_value = 5

Both are integers from 1 to 10.

ambition_value
  How impressive, bold, or scope-expanding this feature is.
  When a player places this card on the board, it adds this many
  Ambition points to their run total.

  Low (1-3)   Small quality-of-life additions.
              Examples: button remapping, mini-map, skip cutscene

  Mid (4-6)   Named systems with real design scope.
              Examples: crafting, faction reputation, dynamic weather

  High (7-9)  Pillar features that define a genre.
              Examples: procedural generation, fully voiced protagonist

  Max (10)    The game-changing promise that will definitely slip.

instability_value
  How technically risky, buggy-prone, or chaotic this feature is.
  When placed, it adds this many Instability points to the run.
  High instability can trigger negative events and jank combinations.

  Low (1-3)   Boring but safe. Static menus, cosmetic items, credits screen.

  Mid (4-6)   Can explode under pressure. Physics, AI, streaming content.

  High (7-9)  Will cause a regression eventually. Guaranteed.
              Examples: destructible environments, horse physics, live service.

  Max (10)    Day-one patch bait. The studio will be fine.

General rule: a feature that is hard to promise should have high ambition.
A feature that is hard to implement should have high instability.
A feature that is both is a candidate for your project's final boss.


STEP 5 -- tier
---------------
  tier = "common"

Leave this as "common" unless the developer assigns a different tier.

What the tiers mean in-game:

  "common"    Standard cards. Grey border. Makes up most of the card pool.

  "uncommon"  Slightly rarer. Steel-blue border. Offered less often as rewards.

  "rare"      Very rare. Gold border with a thicker frame. High-impact cards.

  "jank"      Purple border. Reserved for virtual jank cards generated during
              jank combination events. Do not use for custom cards.

Tier affects how often the card is included in offer pools after a run.
It also changes the visual border colour on the card widget.


STEP 6 -- unlock_weight
------------------------
  unlock_weight = 1.0

Leave this as 1.0 unless you want to bias how often the card appears
as a post-run unlock reward.

The weight is a multiplier relative to other cards in the same offer pool.

  1.0   Normal. Same chance as any other card of the same tier.
  2.0   Twice as likely to be offered.
  0.5   Half as likely. Makes the card feel rarer even within its tier.
  3.0   Floods the pool. Use sparingly.

If you are not sure, leave it at 1.0. The developer can tune it later.


STEP 7 -- tags
---------------
  tags = PackedStringArray("tag_one", "tag_two")

Tags describe what kind of feature this is.
The game uses tags to detect when two cards on the board share a trait
and then fires interactions between them.

Use as many tags as genuinely apply. Do not add tags just to trigger bonuses.

Available tags:

  ai              AI characters or enemy behaviour systems
  animation       Character or object animation rigs and blends
  audio           Sound effects, music systems, voice acting
  building        Base building, construction, or placement systems
  combat          Any system primarily about fighting
  crafting        Item creation, recipes, or material systems
  dialogue        Conversation systems, voiced or text
  economy         Currencies, shops, taxes, trade
  environmental   World systems: weather, day/night, terrain
  faction         Reputation, allegiance, political systems
  inventory       Item management, UI grids, loot screens
  movement        Locomotion: running, climbing, swimming, flying
  narrative       Story, lore, cutscenes, world-building
  online          Multiplayer, co-op, live service, leaderboards
  physics         Ragdolls, destruction, cloth, fluid, vehicles
  platforming     Precision movement on surfaces
  progression     XP, levels, skill trees, unlocks
  pvp             Player-versus-player mechanics
  rendering       Visual effects, shaders, lighting, shadows
  rpg             Character stats, classes, equipment
  shooter         Guns, projectiles, aiming, recoil
  simulation      Emergent systems: ecology, economics, governance
  social          NPC relationships, companions, guilds
  stealth         Hiding, distraction, and detection
  survival        Hunger, thirst, temperature, resource pressure
  traversal       Map exploration: fast travel, mounts, vehicles
  ui              Menus, HUD elements, accessibility options


STEP 8 -- interactions
-----------------------
  interactions = {}

Interactions define stat changes that fire when this card is on the board
and at least one other card on the board shares one of its tags.

Leave as {} to have no interactions for this card.

To add interactions, use this format:

  interactions = {
      "tag_name": {"instability": 2, "soul": -1},
      "other_tag": {"instability": -1, "soul": 0}
  }

  instability   Positive = adds instability when the tag pair appears.
                Negative = reduces instability (a stabilising combination).

  soul          Positive = grants soul (morale boost when features fit together).
                Negative = costs soul (tonal mismatch, design debt, etc.)

Example: a card that gets worse around other physics systems:

  interactions = {
      "physics": {"instability": 3, "soul": -1}
  }

Example: a card that rewards narrative coherence:

  interactions = {
      "dialogue": {"instability": 0, "soul": 2},
      "narrative": {"instability": -1, "soul": 1}
  }

You do not need to cover all your tags. Only write interactions for
the combinations you specifically want to design.


STEP 9 -- interaction_flavor
-----------------------------
  interaction_flavor = {}

Leave this as {}. It is reserved for the developer.


STEP 10 -- archetype_affinity
------------------------------
  archetype_affinity = PackedStringArray("rpg", "action_adventure")

This tells the game which genres this feature naturally belongs to.
When the player runs an archetype (genre) that matches, the card has
reduced soul cost or other minor benefits. Wrong-genre placement costs soul.

Available values: "rpg"   "shooter"   "action_adventure"

You can include one, two, or all three. List only the ones where this
feature genuinely makes sense for the genre.


FINISHED -- what to check before submitting
-------------------------------------------
  [ ] filename is lowercase, underscores only, ends in .tres
  [ ] "template" does not appear in the filename
  [ ] feature_name is not the placeholder text
  [ ] tags is not empty
  [ ] ambition_value and instability_value are integers, not floats
  [ ] tier is "common" (unless told otherwise)
  [ ] unlock_weight is 1.0 (unless you have a reason to change it)
  [ ] The first six header lines are untouched
  [ ] Saved as plain text, not Word or rich-text format
